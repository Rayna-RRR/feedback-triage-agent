# Product Note

## 为什么用户反馈分诊适合做 Agent Demo

用户反馈分诊天然包含多个连续步骤：读取数据、校验字段、理解文本、判断类型、评估风险、生成问题卡片、检查质量和导出报告。每一步都有明确输入和输出，也都有失败或不确定的情况，适合展示 Agent 的工具调用和状态管理。

相比单次文本分类，反馈分诊更接近真实 AI 产品工作：产品助理不只需要知道用户说了什么，还要把反馈转成可以开会讨论、排优先级、进入需求池或进入风险处理的问题。

## Agent 和普通脚本的区别

普通脚本通常是一次性数据处理：输入文件，执行函数，输出结果。

这个项目里的 Agent 更强调：

- 目标：完成用户反馈到产品建议的分诊闭环。
- 工具：每个步骤都是独立 tool，并返回结构化 `ToolResult`。
- 执行状态：runner 维护原始数据、分类结果、问题卡片、QA 摘要和输出路径。
- 日志：`run_log.md` 记录每一步做了什么、产出了什么、下一步是什么。
- 人工复核队列：Agent 不假装所有样本都能自动闭环，而是明确标记需要人判断的边界。

## AI 在流程中负责什么

在 v0.4 中，AI 能力可以来自两层：没有 API key 时使用可解释规则模拟；设置 `DEEPSEEK_API_KEY` 后使用 DeepSeek 生成初稿。AI 可以负责：

- 生成问题分类草稿。
- 摘要用户原话。
- 提炼用户需求。
- 给出初步产品建议。

这些能力适合做初筛和草稿，不适合直接替代最终产品判断。优先级、QA 检查、fallback 和人工复核队列仍由本地规则执行。

RAG、向量数据库和文档检索暂不实现，后续只有在引入产品文档、FAQ 或历史工单时再评估。

## 人为什么必须参与

用户反馈里常见信息缺失、夸张表达、多问题混合和业务上下文不足。特别是 P0、隐私、支付、内容安全、数据丢失等问题，错误判断会带来用户损失或产品风险。

人工复核的价值是：

- 补充业务上下文。
- 判断是否真实可复现。
- 决定是否升级为事故、需求或观察项。
- 对 AI 的分类和建议进行校准。

## 如何迁移到 AI 产品实习 / 产品助理工作

这个项目可以迁移到实际工作中的多个场景：

- 应用商店评论周报。
- 客服工单初筛。
- AI 助手 badcase 收集。
- 需求池输入材料整理。
- 版本发布后的体验问题复盘。

作品集表达重点是：不只会使用 AI，还能设计 AI 参与工作流的边界，并把非结构化输入转成可复核、可追踪、可协作的产品产物。
